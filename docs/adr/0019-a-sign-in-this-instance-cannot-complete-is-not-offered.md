# A sign-in this instance cannot complete is not offered

Whether Brieflyy offers Google is a property of the deployment, not of a request, and the application was answering it three different ways. `createApp` built an `OAuthClient` only when `OAUTH_PROVIDER` named one, so on an instance without Google there was nothing to talk to — but the sign-in page rendered the button unconditionally and both Google routes called straight into the service, which threw `Google OAuth is not configured on this AuthService`. The result was a button that led to a document containing an exception.

The decision is that one answer (`AuthService.googleSignInAvailable()`, which is the question the client itself answers) reaches the page and the two routes, and each of them acts on it. The page does not render the button, or the divider above it that promises a choice the instance does not have. The routes are still registered — they are in the public-route allowlist and the route guard enumerates them — and each refuses with a 503 and a page.

**The routes stay registered rather than being conditional.** Registering them only when a provider exists reads tidier and is what the README claimed the code did, but it makes the public surface of the application depend on a deployment variable: the route guard's allowlist would have to become conditional too, and the guard is the thing that stops an unguarded route being added quietly. A guard that changes shape with the configuration is a guard that checks less. So the routes exist on every instance, refuse on the ones that cannot serve them, and the refusal is part of the surface a test can hold down.

**The refusal is 503, not 404.** The route exists and the deployment is what is incomplete; a 404 would claim the address has never existed, which is false about the code and untrue in a way that is harder to debug than a 503. It is a page rather than JSON because the caller is a person who followed a link off a button — an address that reaches a Google route on an instance with no Google is a bookmark, a forwarded email or a copy of a link from before the provider was removed, and the page is the only place that can say what is missing and offer the way in that does work. It states `account: null` for the reason ADR-0009 records: it is reached on the way in, so there is no signed-in User to put a header on.

**The refusal is not an error page.** It is a 503 with a page of its own, one level below the handler in ADR-0018. Nothing failed here; a capability is absent, and a page that said "Something went wrong" about a deployment decision would be reporting a bug that does not exist. It also answers before the callback route clears its OAuth cookies or reads a code, because a request that cannot be completed has nothing to clean up.

One consequence worth writing down: a deployment that loses its Google configuration stops offering Google rather than breaking, which is the correct failure for a self-hosted Brieflyy but means nobody notices until a User says the button is gone. That is the right way round — the alternative is a button that 500s — and it is the reason the handler exists at all.
