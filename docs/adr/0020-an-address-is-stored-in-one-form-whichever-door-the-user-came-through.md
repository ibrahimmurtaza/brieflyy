# An address is stored in one form, whichever door the User came through

A magic link normalised the address it was sent to: trimmed, lowercased, and refused if it was not an address. The Google path did not normalise what Google returned. `Iris@Example.com` from Google and `iris@example.com` from a magic link are the same human, and the Account is one per human — but the Google sign-in looked the address up as it arrived, found nothing, and made a second User and a second Account for one person. The second Account was not a rare state either: Google does not promise a case, and every Google sign-in by a User who had arrived by magic link before was a candidate for it.

The rule is now one rule. `emailSchema` — trimmed, lowercased, at most 254 characters, and a real address or nothing — is applied wherever an address becomes an Account's, including the claim from Google's verified id token. The magic link path is unchanged; it was already the rule, and it stays the definition rather than becoming one implementation among two.

**An address Brieflyy will not store refuses the sign-in.** A verified Google email that fails the same check a typed one fails gets `unusable_email`, a 400 page, and a sentence pointing at the magic link rather than at the validation error. The alternative — trimming and lowercasing whatever arrives and storing it — is one line instead of a refusal, and it means the Account column accepts values that can never be looked up by the address they contain: a stored ` Iris@Example.com ` is an Account no magic link and no Google sign-in will ever find, because every path into an Account normalises before it looks. Refusing keeps the invariant that an Account's email is an address the application can find it by.

**The Account that is found keeps the address it has.** Normalising is how the lookup matches, not a second version of the row: a magic-link Account stores `iris@example.com`, and a Google sign-in of `Iris@Example.com` joins it and leaves it alone. Rewriting it would move an address a User had already been sent mail at, for no gain.

**The lookup is still exact, and the addresses make that safe.** `accounts.email` is compared with `=`, not `lower()`, and this does not add a case-insensitive comparison: every write goes through `emailSchema`, so what is stored is already in the one form the comparison uses. Making the query case-insensitive instead would be the second fix for the same defect — two answers to "what counts as the same address", one of which the schema cannot enforce.

The race this ticket did not close is named here so it is not mistaken for closed: two concurrent sign-ins for one fresh address — a magic link and a Google callback, or two Google callbacks for two subjects on the same address — can both find no Account and both try to insert one. The unique index on `accounts.email` refuses the loser, after its `users` row is written, so the sign-in fails and an orphan User is left behind. The magic-link path handles that by adopting the account the winner made; the Google path does not, and now answers ADR-0018's page instead of a bare 500.
