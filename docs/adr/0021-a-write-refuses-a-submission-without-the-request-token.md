# A write route refuses a submission whose form does not echo the request token

**Amended by [ADR-0022](0022-a-route-that-changes-state-declares-it.md)**: the check is no longer a line in the Feedback route. A route that changes state declares it, and one hook refuses what it did not make. The reasoning below still holds — the pair, the cookie rather than a stored token, the token that is not per-request, and the page rather than a bare 403 — but "the check is one line in a route rather than a hook" and "a write route that wants the defence asks for it" no longer describe this repository. Read those two paragraphs as the decision that was made once and then replaced, and ADR-0022 for why.

Every state-changing route trusted the session cookie alone. The only thing between a page on another site and a User's Account was the `SameSite` setting on that cookie — a browser default rather than a decision this application makes, tests, or can change from a route. Nothing on a Brieflyy page said "this came from here", so nothing could be checked.

There is now a request token (`src/http/request-token.ts`): a random value the application writes into an httpOnly cookie on the first page a browser is handed, and puts in every POST form on every page it renders afterwards. A route that checks the pair refuses a submission whose cookie and form field are missing, or disagree. The Feedback write is the first route to check it; the rest carry the field already, so each of them is one line rather than a different mechanism.

**The pair, and why two halves.** The cookie alone would be readable by script on the page (`document.cookie`), so it is httpOnly — that flag is the half an injected script cannot get at, and it is why the check cannot read the cookie alone. The form field alone would be a value any page could invent, so it is only accepted when the cookie names the same one. A submission that has to produce a value neither its author nor its User's browser could have known is not a forged submission. What is *not* claimed: that the value in the markup is unreadable. It is in the document, and anything in the document is readable by whatever reads the document. Script running on a Brieflyy page already has the User's session and their data; the token is not what stops that, and no form-carried token could be.

**Why a cookie pair rather than a stored token.** The alternative is a server-side session-to-token mapping, which is what the framework's synchroniser-token pattern does: it survives a cookie the attacker plants, at the cost of a row per User and a lookup per write. Brieflyy has no secret to sign a token with, no place to keep such a row that is not the `sessions` table, and no deployment that runs more than one instance today. A signed cookie would need the same secret. The unsigned pair has one real weakness, and it is a weakness worth naming rather than one worth paying a table for: anything that can set a cookie for the Brieflyy host — a subdomain of it, or a network position between the browser and the application — can fix both halves. Such an attacker can already do that to a session cookie, and to every other cookie the application sets.

**Why the token is not per-request.** Rotating on every response would make two open tabs refuse each other's submissions: the first submission would spend the token, and the tab that had not submitted yet would name a value the cookie no longer had. One token per browser, replaced only when the browser has none, is what makes a form that sat open overnight work when it is finally pressed.

**Why the check is one line in a route rather than a hook.** `installRequestToken` sets the cookie and remembers the value; it does not decide which routes are writes. Hooking "every non-GET route" would have made the unsubscribe one-click POST — authorised by a token in its URL, and sent by mail clients that have no Brieflyy page to carry a field — fail, along with the JSON `/api` routes, which are called by machines rather than by forms. A write route that wants the defence asks for it, which is why one route has it and the rest are visibly without it.

**Why a page, and not a bare 403.** ADR-0018's rule is that every answer is a page or a body; the caller of a form submission is a browser mid-submission, and the two ways it got here are worth saying out loud — a User whose tab went stale, and a page elsewhere trying to spend their session. Both are answered the same way, and neither is answered with a detail about which half matched, because telling an attacker which half they got right makes the next attempt cheaper. The refusal is answered before the body is read for anything: what a forged submission says about a Cluster is not worth answering.
