# A route that submits something declares it, and one hook refuses what it did not make

#83 gave every form in the application a token to echo and put the check in the Feedback route. Every other write still trusted the session cookie alone, and the guarantee was true of one route rather than of the application.

A route now says what it is: `config: { stateChange: 'guarded' }` alongside the access level it already declared, and `src/http/write-guard.ts` reads that in an `onRoute` hook and refuses a submission the request-token cookie does not agree with. `WRITE_GUARD_EXEMPTIONS` in `src/http/access.ts` names the three writes that are not behind it, each with the reason. `src/http/write-guard.test.ts` enumerates the routes `createApp` registers and fails the build for one that submits something and declares nothing and is not named there.

**Why a declaration rather than a line in each route.** A check a route has to remember is a check a route can leave out, and there is no way to tell from reading one route whether it is the last one without it. The declaration moves the decision to where the guarantee is claimed — the manifest — and makes the two impossible to disagree: the route says what it is, the hook says what that means, and the test walks the real application rather than a list somebody kept.

**Why a hook rather than "every non-GET route".** The objection in ADR-0021 still stands: the one-click unsubscribe is sent by a mail client with no Brieflyy page to carry a field. A route-level hook is what puts the check where ADR-0021 wanted it — after the instance hooks have resolved the session, so the refusal can carry the shell, and before the handler, so a submission is refused before the body is read for anything. A *declared* hook keeps the thing ADR-0021 objected to, which was the blanket rule rather than the mechanism.

**A request with no session is left to the route.** There is nothing for it to spend: an authenticated route sends it to `/signup` before a handler runs, and the one public write that reads a session cookie finds none. Answering it here would replace the true answer with a false one — a sign-out button on a tab that had already been signed out would report a forgery — and would take that answer away from `src/http/route-guard.test.ts`, which holds every route to it. What a page elsewhere can cause always carries the session cookie, so that is the case the guard reads.

**Signing out is a state change.** `POST /auth/logout` is public, because a signed-out User asking to be signed out cannot fail, and it is behind the guard anyway: it is the one write that costs an attacker nothing and costs the User everything, since nothing else of theirs is touched and the session simply stops.

**What the guard does not do.** It does not stop a User's own script on a Brieflyy page from submitting their own forms — that script already has the session, and the token is in the document it is running in (ADR-0021). It does not protect the three exempt writes, which have no Brieflyy page behind them: the two one-click unsubscribes, sent by a mail client, and a magic-link request, whose caller is the sign-in page's own script — with no signed-in User there is no page carrying the field it would echo, and it spends no session either. Adding a write means declaring it, and not declaring it means naming it there with the reason — which is the reviewable act ADR-0021 asked for, made true of every write rather than of one.

**An operator's script is not an exemption.** `POST /api/ingest/tick` runs a whole ingest cycle against a User's session, so it sits behind the guard like any other write: its caller fetches a page and echoes the token. The temptation was to call it "a machine, and machines do not carry tokens", which is true of the caller and says nothing about the danger — the request that matters is the one a page elsewhere causes, and what the browser attaches to it is the User's session cookie. A resource an attacker can make a signed-in User's browser burn is exactly what this guard exists for, and its only other protection was the `SameSite` setting ADR-0021 refuses to rely on.

**Two routes that change state are not behind the guard, because a GET cannot carry a token.** `GET /auth/magic-link/verify` and `GET /auth/google/callback` write a session. The token pair checks a submission, and a link followed from an inbox is not one: the emailed link is built before any browser holds a cookie, so it could not echo a value the application would then compare. A stranger can therefore send a reader to a verify link for their own address and sign them into the attacker's account, and nothing here stops it. It is written down rather than left for a reader to assume otherwise — `write-guard.test.ts` names both routes, and CONTEXT.md records it as not built — because a guard that reads as a guarantee it is not making is worse than one that says where its edge is. Closing it needs a second mechanism (a token bound to the address, or an `Origin` check on the two routes), which is a decision of its own.
